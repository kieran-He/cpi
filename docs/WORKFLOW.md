# 数学建模竞赛工作流

## 阶段 0：仓库与比赛确认

运行 `scripts/check_repo.ps1`，确认 `docs/CONTEST_SCOPE.md` 中的比赛信息和规则来源。未确认规则前，不冻结论文页数、格式或最终提交文件。

## 阶段 1：建模手交付

负责人 A 阅读题目与全部附件，完成：

- 根目录 `题目分析报告.md`；
- 根目录 `术语表格.md`；
- `analysis/model_contract.md`；
- `analysis/validation_plan.md`。

每个子问题至少写明：目标、输入、假设、变量、单位、约束、模型、算法、输出和验证方法。状态只有在两人核对后才能从 `DRAFT` 改为 `READY`。

## 阶段 2：编程手最小闭环

负责人 B 先实现一个最小可运行切片，从真实输入或结构等价小实例产生一个可检查结果。随后再做全量计算、参数扫描和正式绘图。

建议代码分层：

- `src/data/`：读取、清洗、单位转换；
- `src/models/`：模型和约束；
- `src/experiments/`：参数、批量实验、敏感性分析；
- `src/visualization/`：出版级绘图函数；
- `src/common/`：路径、日志、随机种子和公共工具。

## 阶段 3：结果冻结

结果进入 `results/`，图表进入 `figures/`。图表文件名按 `raw_q1_*`、`process_q1_*`、`result_q1_*`、`flow_overall_model.*` 组织。关键结果必须能由一个唯一命令重新生成，并记录输入哈希、种子、参数和依赖版本。

## 阶段 4：论文整合

论文只引用已经冻结的结果。A 负责叙事和公式，B 负责核对图表、数值和代码路径。论文模板、页数、匿名和提交格式必须服从当届官方规则。

## 阶段门禁

```text
题目/附件 → 模型合同 READY → 最小运行 → 全量结果 → 图表审查 → 论文草稿 → 双人交叉复核 → 提交包
```

任何上游模型、参数、数据或规则发生实质变化，都要回退并重跑受影响阶段。
